# 校务 AI 数据采集与知识管理中台 · 设计规格（Spec）

- 日期：2026-08-18
- 状态：已确认（待实现计划）
- 项目仓库：https://github.com/zgozh/school-knowledge-hub

## 1. 项目背景与定位

**大赛背景**：人工智能创新应用大赛，赛道聚焦教育领域与湾区治理真实场景的技术瓶颈。选题主题：**面向校务管理的 AI 自动数据采集与知识管理中台**。评审形式：演示视频 + 文档。

**立项三问（project-kickoff，已确认）**：

1. **给谁用、解决什么痛点**：给广州大学的师生与校务行政人员用，解决"校务信息散落在官网、新闻网等多处，办事流程与制度规定不知去哪查"的痛点——系统自动采集多源信息形成统一知识库，用自然语言提问即可获得附来源的可信答案。
2. **硬约束（不可妥协）**：
   - 答案可信：每条回答必须附来源引用（标题/栏目/日期/链接），无来源不编造；
   - 一台机器稳定复现：全链路可在单机 Docker Compose 上稳定跑通、反复录制演示；
   - 零内网依赖：不依赖学校内部系统权限，公开网页 + 模拟数据即可完整运行。
3. **第一版砍掉**：评测闭环 RAGAS（扩展项）、用户登录/权限体系、多租户/多学校、移动端适配、附件上传问答、微信公众号采集、大屏可视化；多轮对话仅做简化版（最近 N 轮历史），不做长期记忆/个性化。

**主题贴合度**（四要素全覆盖）：

| 主题要素 | 落地方式 |
|---------|---------|
| 面向校务管理 | 通知公告、办事指南、制度规定、新闻网多源校务信息 |
| AI 自动数据采集 | 定时调度、多源爬虫、增量去重、清洗解析、LLM 兜底提取、自动分类打标、任务监控 |
| 知识管理 | 自动分类打标、专题知识域、全生命周期（生效→到期→归档/降权）、知识资产全景、知识治理（近重复检测/异常标记） |
| 中台 | 双端（管理端+问答端）、三服务分层、存储服务化、数据资产化 |

## 3. 创新点定位

- **主创新 1：多源异构自动采集管道**——多站点/多栏目自动发现、增量采集去重、HTML 清洗归一、失败重试、管理端可视化监控，把"自动采集"做实。
- **主创新 2：可信问答**——答案附来源引用（标题/栏目/日期/链接/原文快照回溯）；检索排序含时间衰减（通知类时效敏感）；过期内容降权并标注。
- **辅助 3：湾区特色知识域**——新生入学指南、港澳生服务、跨校区办事等专题知识域。
- **辅助 4：知识全生命周期管理**——采集→清洗→打标→入库→到期检测→归档，管理端知识资产统计。
- **扩展（第一版不做）**：评测闭环 RAGAS。

## 4. 整体架构

三服务分层 + 双端界面 + 存储全复用：

```
┌─────────────────────────────────────────────────────┐
│                  前端（Vue 3 SPA）                    │
│     管理端：采集源配置·任务监控·知识库管理·资产全景     │
│     问答端：聊天界面（SSE 流式 + 来源引用卡片）         │
└──────────────┬───────────────────────┬──────────────┘
               │ HTTP/SSE               │ HTTP
┌──────────────▼────────────┐ ┌─────────▼───────────────┐
│    问答服务 (qa-api)       │ │   采集服务 (collector)    │
│  检索→重排→LLM流式生成      │ │ 调度→爬取→解析→向量化→入库  │
│  来源引用·问答日志          │ │ 任务状态·增量去重·重试      │
└──────────┬────────────────┘ └──────────┬───────────────┘
           │                             │
      ┌────▼─────────────────────────────▼────┐
      │    本地模型服务（FlagEmbedding FastAPI）   │
      │  BGE-M3 双向量(dense+sparse) + reranker  │
      └─────────────────────────────────────────┘
           │
┌──────────▼─────────────────────────────────────────────┐
│              共享存储（Docker Compose 统一编排）           │
│  Milvus    → 向量检索（dense+sparse 混合）                 │
│  MongoDB   → 元数据/任务状态/问答日志/统计                 │
│  MinIO     → 原始HTML快照·附件                            │
└─────────────────────────────────────────────────────────┘
           ▲
   DeepSeek（主 LLM）/ DashScope（降级兜底）
```

**职责边界**：采集服务 = 知识的生产与治理（采集、打标、生命周期、统计、管理端 API）；问答服务 = 知识的消费（检索、重排、生成、问答日志）。服务间不互相调用业务逻辑，只通过 HTTP API 与共享存储通信。

## 5. 数据流（四条主线）

1. **采集流**：定时触发 → 抓列表页 → 增量对比（URL+内容哈希）→ 抓详情页 → 正文提取清洗 → 元数据抽取 → 时效标注 → 切分 → BGE-M3 向量化 → Milvus + MongoDB + MinIO 三写 → 任务日志。
2. **问答流**：提问 → 混合检索（dense+sparse，norm_score 归一化，时间衰减，过期降权）→ bge-reranker 精排 → 组装上下文 → DeepSeek 流式生成（SSE）→ 来源引用 → 问答日志。
3. **管理流**：配置采集源 → 触发/监控任务 → 知识资产全景 → 到期检测归档 → 人工上下架/修正。
4. **知识管理流**：入库 → 自动分类打标（一级规则/二级 LLM）→ 时效标注 → 资产统计 → 到期归档/降权 → 人工审核 → 资产全景展示。

## 6. 组件设计

### 6.1 采集服务（collector）

| 组件 | 职责 |
|------|------|
| 调度器 | APScheduler 定时触发各采集源任务（周期可配） |
| 采集源管理 | 采集源 CRUD（站点/栏目/类型/抓取规则/启用状态） |
| 爬虫模块 | httpx+selectolax 抓列表页/详情页；站点适配器模式（主站/新闻网各一个，新增站点只写适配器） |
| 去重模块 | URL 哈希 + 内容哈希增量判定 |
| 解析模块 | trafilatura 正文提取 + 元数据抽取；失败时 DeepSeek 兜底结构化提取 |
| 打标模块 | 一级分类（规则）+ 二级专题域（LLM 批量打标，可离线批处理） |
| 时效模块 | 有效期推断（截止日期识别 + 类别默认时效） |
| 入库模块 | 切分 → BGE-M3 向量化 → Milvus 向量 + MongoDB 元数据 + MinIO 快照三写 |
| 任务管理 | 任务状态机（待运行/运行中/成功/部分失败/失败）、日志、重试 |
| 生命周期 | 到期检测定时任务 → 归档/降权；人工上下架 API |
| 统计模块 | 知识资产聚合（采集量/分类分布/时效分布/问答热度） |
| API 层 | 管理端全部接口 |

### 6.2 问答服务（qa-api）

| 组件 | 职责 |
|------|------|
| 检索模块 | Milvus hybrid（dense COSINE 0.8 + sparse IP 0.2，norm_score 归一化）+ 分类/专题域元数据过滤 + 时间衰减 + 过期降权 |
| 重排模块 | bge-reranker-large 精排（召回 top10 → 断崖截断） |
| 生成模块 | DeepSeek 主 / DashScope 降级，SSE 流式，提示词模板外置 |
| 引用组装 | 来源卡片（标题/栏目/日期/链接/MinIO 快照回溯） |
| 对话模块 | 简化多轮（最近 N 轮历史拼入提示词） |
| API 层 | `/chat` SSE 流式 + 问答日志写 MongoDB |

### 6.3 模型服务（model_server）

- FlagEmbedding 自建 FastAPI：`POST /embed`（BGE-M3 dense+sparse 双输出）、`POST /rerank`（bge-reranker-large）。
- 模型权重挂载本地路径（不依赖运行时下载）：
  - BGE-M3：`D:\ai_models\huggingface_cache\bge-m3\models\BAAI--bge-m3\snapshots\master`
  - Reranker：`D:\ai_models\modelscope_cache\models\BAAI--bge-reranker-large\snapshots\master`

### 6.4 前端（Vue 3 SPA，单应用双布局）

- 问答端 `/`：聊天界面（SSE 流式 markdown 渲染 + 来源引用卡片 + 专题域筛选）
- 管理端 `/admin`：资产全景仪表盘、采集源管理、任务监控、知识库管理（分类/专题域/时效状态/上下架）、统计图表

### 6.5 目录结构

```
school-knowledge-hub/
├── collector/            # 采集服务（重任务）
│   ├── api/              #   管理端 API 路由
│   ├── scheduler/        #   APScheduler 调度
│   ├── crawler/          #   爬虫 + 站点适配器
│   ├── parser/           #   正文提取 + 元数据
│   ├── tagger/           #   分类/专题域打标
│   ├── lifecycle/        #   时效与生命周期
│   ├── ingest/           #   切分/向量化/三写入库
│   └── tasks/            #   采集任务状态机
├── qa_api/               # 问答服务（低延迟）
│   ├── api/              #   /chat SSE
│   ├── retriever/        #   混合检索 + 时间衰减
│   ├── reranker/         #   精排
│   ├── generator/        #   LLM 流式生成 + 降级
│   └── prompts/          #   提示词模板（与逻辑分离）
├── model_server/         # FlagEmbedding 模型服务
├── shared/               # 共享库：配置 dataclass、MongoDB/Milvus/MinIO/LLM 客户端单例、基类
├── frontend/             # Vue 3 SPA
├── docs/                 # spec/ADR/计划文档
└── docker-compose.yml    # 全部服务编排（含 Milvus/MongoDB/MinIO）
```

**关键原则**：`shared/` 只放跨服务复用件；业务逻辑不跨服务调用；横切关注点（日志/异常/重试）在 shared 基类收敛。

## 8. 错误处理与降级策略

- **降级链**：DeepSeek 挂→DashScope；reranker 挂→跳过精排；sparse 异常→仅 dense；embedding 挂→采集任务退避重试/问答明确报错；MinIO 挂→跳过快照标记缺失；MongoDB 挂→日志降级文件；元数据过滤失败→不带过滤检索。主链路永远可用。
- **采集容错**：单页失败不拖垮整批；指数退避重试最多 3 次；幂等入库（哈希查重）；任务状态机全可见；LLM 打标失败→规则兜底。
- **问答可信**：检索为空→诚实回答"未找到"+建议方向，绝不无来源编造；过期知识→降权+标注；SSE 中断→保留已生成部分+可重试；LLM 超时 30s→降级模型→友好报错。
- **全局**：外部调用统一超时（默认 10s 可配）；配置外置 `.env`→dataclass，`.env.example` 进 git、`.env` 不进；结构化日志任务 ID/请求 ID 贯穿；异常收敛 shared 基类。

## 9. 测试策略与验收标准

### 单元测试（pytest + TDD）
解析模块（真实 HTML fixture）、去重、时效推断、打标规则、时间衰减、norm_score 融合（mock）、切分。

### 集成测试
1. 全链路：模拟数据 → 采集（mock 站点）→ 入库 → 检索 → 问答 → 来源引用（5~10 篇真实跑）
2. 降级路径：reranker 不可用→检索兜底；DeepSeek 不可用→DashScope 兜底
3. 幂等：同一任务跑两遍不产生重复数据

### 不做
重型前端 e2e、RAGAS 自动化评测（扩展项）。保留 20 题演示问题清单（手工验收素材+路演脚本）。

### 验收标准（对应硬约束）
1. 答案可信：20 题清单答案带来源引用率 100%，无来源不编造；
2. 单机稳定复现：空环境一条 `docker compose up` 起全栈，集成测试通过；
3. 零内网依赖：不依赖学校内网与内部权限即可完整演示。

## 10. 人工准备清单

1. 中间件：开发期用 WSL 现有 Milvus/MongoDB/MinIO；最终统一编进项目 docker-compose 一起部署。
