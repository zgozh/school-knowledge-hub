# ADR-011: 开发模型分工与批量派活

- 日期：2026-08-18
- 状态：已接受

## 背景
用户指定模型分工：前端开发用 kimi-k3、后端开发用 glm-5.3、调度/脚手架/规划用 deepseek-v4-pro（主会话）。且要求不每次创建新子代理做小开发。

## 决策
- 主会话（deepseek-v4-pro）：调度、脚手架、规划、评审、集成。
- 后端代码（collector/qa_api/model_server/shared）：主会话用 `workflow` 批量派发，`agent(prompt, {model: 'glm-5.3'})`。
- 前端代码（frontend）：主会话用 `workflow` 批量派发，`agent(prompt, {model: 'kimi-k3'})`。
- 按阶段批量派发（一次 workflow 覆盖一个阶段多个 bite-size 任务），任务简报完全自包含。
- **每个任务必须「最小实现 + 小 commit + 真实验收」**：子代理报告完成不算数，主会话评审时逐任务核验文件与测试，未实现不得标记通过。

## 备选
- 固定 durable subagent 复用：DSH 实测 `subagent` 工具无 model 参数（只有 description/prompt/run_in_background），无法指定模型——否决。
- 逐个小任务派发：上下文重建成本高——否决（改用阶段批量）。

## 后果
- 正面：模型分工满足；批量派发控制上下文开销；简报自包含保证子代理不依赖前序对话。
- 硬约束关联：派活规则写入 AGENTS.md，主会话执行时强制遵守。
- 重新评估触发：若 DSH 后续版本 subagent 工具支持 model 参数，或单个任务过大导致批量失败率高，调整派活粒度。

## 人工资源依赖
无。
